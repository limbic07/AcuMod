# 功能拆分

Acumod 的功能按“先传统管理器，后 AI Agent”的顺序推进。传统管理器必须先具备稳定、安全、可验证的操作能力，AI Agent 后续只调用这些受控能力。

## MVP 范围

MVP 目标：做出一个可真实管理 MHW 本地 MOD 的传统管理器，完成“导入 -> 识别 -> 启用 -> 禁用 -> 卸载 -> 冲突排序 -> 一键还原”的闭环。当前 MVP 已完成。

MVP 必须包含：

- 游戏目录设置：自动检测 Steam 默认安装路径；检测失败后允许手动设置；以 `MonsterHunterWorld.exe` 校验目录；首期只支持一个 MHW 游戏路径。
- 本地配置和元数据：MVP 先使用 JSON 文件保存配置、MOD 元数据、启用状态、排序和部署记录，后续需要复杂查询时再考虑 SQLite。
- 本地 MOD 库：安装 MOD 时在 Acumod 软件目录保存一份，不直接写入游戏目录。
- 导入方式：第一版必须支持文件夹导入，以及 `rar`、`zip`、`7z` 压缩包导入。
- 复制式部署：启用时从 Acumod MOD 库复制到 MHW 游戏目录；禁用时删除游戏目录中的已部署文件；卸载时只删除 Acumod 记录过的文件。
- 部署记录：记录每个 MOD 启用时实际写入的目标路径，禁用、卸载、一键还原都必须基于记录执行。
- 冲突处理：同名目标文件冲突时先提示；提供独立冲突排序功能，让用户通过排序决定最终覆盖优先级。
- 一键还原：禁用全部已启用 MOD，并删除所有 Acumod 记录过的部署文件。
- MHW 文件 ID 表：内置维护一份 MHW 文件 ID 表，用于识别模型替换 MOD 替换了哪些游戏内模型。
- 替换目标识别：第一版覆盖武器、防具、发型、随从武器、随从防具、猎虫、挂件、NPC、投射器和人物语音；同一个 MOD 可能替换多个目标；第一版只做识别和展示。
- 操作预览：启用、禁用、卸载、排序变更、一键还原前展示会影响哪些文件。

MVP 不包含：

- 下载和更新功能。后续如做，只考虑 Nexus Mods，并使用 API 下载和 SSO 登录。
- AI Agent。
- 多个 MHW 游戏路径。
- 模型替换目标选择或改绑。
- 任何修改模型替换目标的功能，包括通过部署路径、文件名或文件内容进行改绑。
- 自动清理 Acumod 没有记录过的手动安装文件。

MVP 完成标准：

- 用户能设置 MHW 游戏目录并通过校验。
- 用户能导入文件夹 MOD 和 `rar`、`zip`、`7z` 压缩包 MOD。
- 用户能看到 MOD 列表、文件列表、启用状态、冲突状态和模型替换识别结果。
- 用户能启用、禁用、卸载 MOD。
- 用户能通过排序解决文件冲突。
- 用户能一键还原纯净状态。
- 所有删除动作只处理 Acumod 记录过的部署文件。

## 阶段 0：基础链路

目标：确认应用能够运行，前端能调用 Rust。

当前状态：

- 已有 Vue 页面。
- 已有 `get_app_info` Tauri command。
- 已有 Rust DTO 返回。
- 已有 Tauri 2 配置和 npm 构建脚本。

完成标准：

- `npm run build` 能完成前端类型检查和构建。
- `cd src-tauri && cargo check` 能完成 Rust 检查。
- `npm run tauri:dev` 能打开桌面窗口并展示后端返回信息。

## 阶段 1：游戏目录和 MOD 扫描

目标：让用户选择或确认 MHW 游戏目录，并扫描当前游戏目录状态。

已确认规则：

- 支持自动检测 Steam 默认安装路径。
- 自动检测失败后，允许用户手动设置 MHW 游戏目录。
- 游戏目录校验以 `MonsterHunterWorld.exe` 为准。
- 不支持多个游戏路径，首期只管理一个 MHW 安装目录。

建议功能：

- 手动设置 MHW 游戏目录。
- 检测目录是否包含 `MonsterHunterWorld.exe`。
- 识别 `nativePC` 目录。
- 扫描当前游戏目录中已有 MOD 文件。
- 展示扫描结果、未知文件和潜在风险。

## 阶段 2：本地 MOD 导入和复制式启停

目标：实现传统 MOD 管理器的核心能力：导入、启用、禁用、卸载。

已确认规则：

- 本管理器目前只使用复制式部署。
- 安装 MOD：在 Acumod 软件目录保存一份 MOD，不直接写入游戏目录。
- 启用 MOD：把 Acumod 保存的 MOD 文件复制到 MHW 游戏目录。
- 禁用 MOD：删除 MHW 游戏目录下该 MOD 的已部署文件，保留 Acumod 软件目录中的 MOD 副本。
- 卸载 MOD：只删除由 Acumod 安装并记录过的文件；如果该 MOD 仍处于启用状态，需要先清理它部署到游戏目录中的文件。
- 同名文件冲突时，启用前弹出提示。
- 需要独立的冲突解决功能，让用户通过排序决定覆盖优先级。
- 第一版必须支持文件夹导入，以及 `rar`、`zip`、`7z` 压缩包导入。
- 用户可将一个 MOD 文件夹或一个支持的压缩包拖入程序任意位置；释放后必须先显示确认弹窗，用户确认后可正常识别的文件夹直接安装到本地 MOD 库，压缩包复用现有解包导入流程；目录歧义时列出候选内容根并只导入用户选择的一个分支，游戏根目录 fallback 继续要求确认；一次拖入多个项目时拒绝处理并提示用户逐个导入。
- 当前压缩包导入实现使用随 Acumod 打包的 7-Zip 解包组件：先解包到 `AcumodData/mods/staging/imports/`，再复用文件夹导入识别和本地 MOD 库安装逻辑；用户不需要另行安装 7-Zip。
- 压缩包解压目录只作为临时导入空间；成功安装后只长期保留所选分支在本地 MOD 库中的一份副本。进程首次访问 MOD 库或开始下一次压缩包导入时清理遗留暂存。
- 导入前按 MOD 名称进行不区分大小写的重复检查；同名 MOD 已存在时返回已有 MOD 信息并显示“已导入”，不创建新的 MOD 目录。压缩包在解包前执行这项检查。
- 导入识别优先以 `nativePC` 为内容根；如果压缩包或文件夹缺少 `nativePC`，但出现 `weapon`、`wp`、`pl`、`plugins` 等常见 nativePC 内部目录，则自动补成 `nativePC/...` 部署路径；如果用户直接选择这些内部目录本身，也要保留目录名并映射到 `nativePC/<目录名>/...`。
- 如果无法识别 `nativePC` 或常见 nativePC 内部目录，但目录内存在文件，应提示用户确认是否按游戏根目录相对路径导入；确认前不能自动把未知目录当作游戏根目录 MOD。
- 当前启用实现：从 Acumod 本地 MOD 库复制到已配置的 MHW 游戏目录；启用前生成部署计划，目标文件已存在时要求用户确认。
- 当前禁用实现：只删除该 MOD manifest 中 `deployedFiles` 记录过的游戏目录文件，并保留 Acumod 本地 MOD 库副本。
- 当前卸载实现：先生成卸载预览；如果该 MOD 有已记录部署文件，先清理游戏目录部署副本；随后删除 Acumod 本地 MOD 库中的该 MOD 目录。
- 当前一键还原实现：扫描 Acumod 本地 MOD 库中的 manifest，禁用所有仍启用或仍有部署记录的 MOD，并删除所有记录过的游戏目录部署文件。
- 当前冲突排序实现：扫描所有已安装 MOD 的 `deployRelativePath` 建立 MOD 冲突关系；直接或间接相互冲突的 MOD 归为一组，彼此无关的冲突分开显示。主列表只显示普通序号；用户在独立冲突界面调整整个组的 MOD 覆盖顺序，不显示具体冲突文件路径。组顺序保存到 `AcumodData/mods/installed/conflict-orders.json`；应用时统一处理组内全部冲突文件，每个文件由顺序中最后一个已启用且实际包含该文件的 MOD 提供。
- 已安装 MOD 列表可以通过受校验的 Tauri command 在系统资源管理器中打开对应本地库 `content` 文件夹。
- 冲突报告只包含至少两个当前已启用 MOD 之间的实际冲突；尚未启用的 MOD 不进入冲突组，也不在冲突管理界面显示。
- 每次成功启用 MOD 后，将它追加到相关冲突组顺序末尾。例如先启用 A、再启用 B，默认顺序记录为 `A -> B`，由 B 覆盖 A；之后用户仍可在冲突管理界面手动调整。
- 如果当前生效 MOD 被禁用或卸载，Acumod 会重新应用它所在冲突组，让顺序中的下一个适用且已启用 MOD 接管；无法安全覆盖时保留警告。

建议功能：

- 从本地文件夹导入 MOD。
- 从本地压缩包导入 MOD。
- 在真正导入前生成路径预览，展示源文件会被映射到 `nativePC/...` 还是游戏根目录相对路径。
- 展示 MOD 名称、来源、安装状态、启用状态、文件列表。
- 启用 MOD。
- 禁用 MOD。
- 卸载 MOD。
- 记录每个 MOD 启用时实际复制到游戏目录的文件列表。
- 对覆盖操作生成预览和确认；MOD 原始文件由本地 MOD 库保存，不额外备份游戏目录中的被覆盖文件。

## 阶段 3：模型替换 ID 表和目标识别

目标：识别 MHW 模型替换 MOD 实际替换的是哪个游戏装备或模型，并显示具体的游戏内名称。

这是 MHW 传统 MOD 管理器的重要能力，不属于 AI Agent 附属功能。

已确认规则：

- MHW 文件 ID 表由 Acumod 内置维护。
- MHW 已停止更新，因此首期可以先维护一版固定 ID 表。
- 第一版识别范围覆盖武器、防具、发型、随从武器、随从防具、猎虫、挂件、NPC、投射器和人物语音替换。
- 同一个 MOD 可能替换多个模型，需要展示多个识别结果。
- 当前内置索引由 `15.10.00` 数据包、本地中文表和可追溯的 curated 社区映射生成；原始游戏数据不提交，应用使用 `references/mhwi-data/curated/model-index.json`。

核心概念：

- MHW 的模型替换 MOD 通常会通过文件路径和文件 ID 指向某个游戏内模型。
- Acumod 需要维护一份 MHW 文件 ID 表，把底层文件 ID 映射为用户能看懂的游戏内名称。
- 识别结果应展示为“这个 MOD 替换了什么”，而不是只展示一串文件名。

当前实现：

- 生成并内置武器、防具模型索引，扫描 MOD 的目标部署路径。
- 武器按模型资源路径识别武器种类、主模型或附件模型、武器 ID 和共用该模型的游戏名称。
- 防具按 `plXXX_XXXX` 模型 ID 和 `helm/body/arm/wst/leg` 部位标记识别装备部位、ID 和游戏名称。
- 发型按 `pl/hair/hairXXX` 路径识别模型 ID，并映射角色创建界面槽位、DLC/NPC/联动名称；Wiki 未收录的编号仍按路径模式返回 ID。
- 随从武器、随从防具、猎虫、挂件和 NPC 使用本地 `15.10.00` 中文表的模型目录、游戏 ID 和名称。
- 武器、防具、发型、随从装备等只在各自规范资源根目录中识别；`vfx/mod` 等特效附属资源不会映射为游戏装备替换目标，但仍会保留在 MOD 文件列表和部署记录中。
- 同一防具模型命中多个部位时合并显示为“防具套装”，并列出实际替换的头部、身体、腕部、腰部和脚部。
- 投射器按 `wp/slg/slgNNN_NNNN` 目录识别，同时兼容旧 `slgNNN` 格式；已知 `slg000_0000` 显示“通用投射器/飞翔爪”，未知编号保守显示底层 ID。
- 人物语音只在 `sound/wwise/Windows` 下精确匹配 `pl_act_vo_f_*_m.nbnk` 或 `pl_act_vo_m_*_m.nbnk`，映射为角色创建界面的男女语音 1 至 20 号。
- 识别结果写入 manifest schema 9，并在导入结果和已安装 MOD 列表展示；schema 1 至 7 manifest 在读取列表时即时补算，schema 8 已保存的识别结果继续直接使用。
- 模型 ID 和装备部位只匹配文件夹名称，文件名不参与模型识别；人物语音因游戏资源格式没有独立 ID 目录，是唯一的精确文件名匹配例外。
- 发型优先显示角色创建界面的数字槽位，再显示经 CAPCOM Steam 页面或本地游戏文本确认的官方简体中文名称；NPC/联动角色英文名不作为游戏 ID 显示。
- 同一个 MOD 可以返回多个 `ModelReplacement`。

后续增强：

- 在冲突处理中按“替换同一个游戏模型”提供额外提示。
- Wiki 社区数据与最终发布包的再分发许可确认。

后续功能：

- 根据文件 ID 表识别结果对 MOD 自动分类，例如武器外观、防具外观、发型替换等。
- 根据模型类型、武器种类、游戏内名称对 MOD 进行筛选和排序。
- 在 MOD 列表中支持按替换目标聚合，例如查看所有替换太刀的 MOD。
- 在冲突排序中优先展示替换同一模型或同一路径的 MOD。

Wiki 与本地 `15.10.00` 数据包中还有可扩展的路径识别类别，均不属于当前 MVP：

- 可继续接入：怪物、脸型、噗吱猪服装、家具、玩家/随从通用附件。
- 特殊装备、物品、装饰品、技能、任务和食堂技能等表主要提供数据 ID，缺少可由普通 MOD 文件路径稳定反推具体对象的映射；在建立文件格式识别前不做路径猜测。
- 数据优先级为本地 `15.10.00` 中文表高于社区 Wiki；Wiki 数据必须记录来源和核验日期，未知项继续保守显示底层 ID。

建议数据：

- 文件 ID。
- 模型类型。
- 子类型，例如武器种类。
- 游戏内名称。
- 原始资源路径或目标部署路径。

## 阶段 4：MVP 单一部署状态、冲突排序和一键还原

目标：更清楚地处理 MOD 之间的文件覆盖关系，并支持恢复纯净状态。

已确认规则：

- 只维护当前这一套启用状态和按冲突组保存的排序；不提供多套配置、状态快照或配置切换。
- 主列表使用普通序号，不提供全局 MOD 优先级。
- 有文件冲突时，用户在独立界面中按相互冲突的 MOD 组分别排序；A/B 与 C/D 这类无关冲突互不影响。
- 支持一键还原到纯净状态。
- 一键还原等于禁用全部已启用 MOD，并删除所有 Acumod 记录过的部署文件。

建议功能：

- 显示 MOD 之间的文件冲突。
- 显示哪些 MOD 互相冲突，以及每组涉及的冲突文件数量，但不在主界面列出具体路径。
- 允许用户调整当前冲突组的整体 MOD 覆盖顺序。
- 调整后为整个冲突组生成应用预览。
- 提供应用计划前的操作预览。
- 提供一键还原纯净状态。

## 阶段 5：下载和更新

目标：帮助用户从外部来源获取 MOD，但不牺牲安全和可控性。

已确认规则：

- MVP 不包含下载和更新功能。
- 后续如实现下载和更新，只支持 Nexus Mods。
- 后续 Nexus Mods 下载需要使用 API 下载和 SSO 登录。

## 阶段 6：AI Agent

目标：让用户用自然语言管理 MOD，但所有动作仍通过传统管理器的受控能力执行。

已确认规则：

- MVP 不包含 AI Agent。
- AI Agent 后续接入时，只能调用传统管理器已有的受控能力。

建议功能：

- 用户输入：“禁用所有画质类 MOD”。
- 用户输入：“把这个太刀外观 MOD 改成替换另一把太刀”。
- AI 解析意图并生成操作建议。
- 应用展示计划：将启用、禁用或改绑哪些 MOD，为什么，影响哪些文件。
- 用户确认后执行。
- 执行结果回写给用户。

后续 AI 能力：

- 智能翻译 MOD 名称和说明。
- 翻译时必须使用 MHW 游戏术语表和文件 ID 表辅助理解，避免把武器名、装备名、怪物名、技能名等游戏术语翻译错。
- 翻译结果应保留原文，并在低置信度时提示用户确认。
- 用户可以用自然语言搜索 MOD，例如“我想安装太刀外观 MOD”。
- Agent 可以联网搜索候选 MOD，并给出来源链接，让用户自行下载和导入。
- Agent 后续可以通过 Nexus Mods API 搜索和下载 MOD。
- 通过 Nexus Mods API 安装时，需要用户完成 SSO 登录或授权。
- Agent 下载或安装前必须展示来源、文件名、影响范围和操作计划，并等待用户确认。

第一阶段 AI 只建议，不直接执行。等传统操作计划、确认和执行记录稳定后，再允许“确认后执行”。

## 已完成：传统管理器增强

本阶段让已完成的传统管理器更适合持续使用；没有接入网络、AI Agent 或模型改绑。

1. Slice 11：UI 架构收尾
   - `AppSidebar`、`AppTopbar`、`FloatingAgentPanel` 负责应用壳；`ModLibraryToolbar` 和 `ModLibraryTable` 负责 MOD 库的检索控制与表格展示。

## 已完成：MOD 库表格重构

本切片重构了 MOD 库的信息层级和编辑方式，不改变既有导入、部署或冲突排序语义：

1. 最左列使用一个固定尺寸的启用按钮，同时表示当前状态并提供启停入口；启停仍必须经过现有预览和确认流程。
2. 序号使用独立固定列，按照当前筛选和浏览排序结果显示。
3. 名称和备注支持表格内直接编辑，使用 `Enter` 或失去焦点提交，`Esc` 取消。
4. 替换信息只展示两行以内的主要摘要，完整识别结果、资源 ID 和文件信息放入行内展开详情。
5. ID 表识别到的每个分类以独立标签展示；用户可以为 MOD 选择一个额外分类，也可以在分类下拉菜单中创建全新分类。
6. 用户分类对整个 MOD 库生效；删除分类后，相关 MOD 只保留 ID 表识别标签，不丢失识别结果。
7. 操作列只保留打开本地文件夹、展开详情和卸载图标；启停和编辑不在操作列重复出现。

分类修改只更新 MOD 元数据，不能改写 MOD 文件、模型识别结果、启用状态或冲突顺序。具体列宽、状态样式、编辑反馈和分类校验规则见 `docs/ui-design.md`。

### 实现约定

- 全局用户分类存放于 `AcumodData/mods/categories.json`，包含稳定分类 ID、名称和创建时间。
- 每个 MOD manifest 只保存可选的 `categoryOverride` 分类 ID。未设置、引用已删除分类或旧 manifest 缺少该字段时，一律回退为自动分类。
- `categories` 继续表示 ID 表自动识别结果；用户分类不能覆盖或修改该字段。列表 DTO 额外返回已解析的用户分类，前端将两者作为并列标签显示，并按任一标签筛选和排序。
- 元数据更新改为字段级 patch：名称、备注和 `categoryOverride` 可以独立保存。空名称表示回到原始导入名称，空分类 ID 表示不设置用户分类。
- 新建、重命名、删除用户分类使用独立的 Tauri command。删除分类时，Rust 扫描本地 MOD manifest 并清除所有对应引用，再删除分类定义；该过程不接触 MOD 内容或游戏目录。
- manifest schema 升级时保持模型识别版本独立：旧 manifest 的分类覆盖字段缺失默认视为未设置，已完成的模型识别结果不因本次元数据升级而重新解释。
- 前端保存链路为：表格单元格或分类管理对话框 -> `src/api/modLibrary.ts` typed wrapper -> Tauri command -> Rust service -> `manifest.json` 或 `categories.json` -> 刷新 MOD 列表和分类列表。
