# 功能拆分

Acumod 的功能按“先传统管理器，后 AI Agent”的顺序推进。传统管理器必须先具备稳定、安全、可验证的操作能力，AI Agent 后续只调用这些受控能力。

## MVP 范围

MVP 目标：做出一个可真实管理 MHW 本地 MOD 的传统管理器，完成“导入 -> 识别 -> 启用 -> 禁用 -> 卸载 -> 冲突排序 -> 一键还原”的闭环。当前 MVP 已完成。

MVP 必须包含：

- 游戏目录设置：自动检测 Steam 默认安装路径；检测失败后允许手动设置；以 `MonsterHunterWorld.exe` 校验目录；首期只支持一个 MHW 游戏路径。
- 本地配置和元数据：MVP 先使用 JSON 文件保存配置、MOD 元数据、启用状态、排序和部署记录，后续需要复杂查询时再考虑 SQLite。
- 本地 MOD 库：安装 MOD 时在 Acumod 软件目录保存一份，不直接写入游戏目录。
- 导入方式：第一版必须支持文件夹导入，以及 `rar`、`zip`、`7z` 压缩包导入。
- 复制式部署：启用时从 Acumod MOD 库复制到 MHW 游戏目录；禁用时删除游戏目录中的已部署文件；卸载时只删除 Acumod 记录过的文件。
- 部署记录：记录每个 MOD 启用时实际写入的目标路径，禁用、卸载、一键还原都必须基于记录执行。
- 冲突处理：同名目标文件冲突时先提示；提供独立冲突排序功能，让用户通过排序决定最终覆盖优先级。
- 一键还原：禁用全部已启用 MOD，并删除所有 Acumod 记录过的部署文件。
- MHW 文件 ID 表：内置维护一份 MHW 文件 ID 表，用于识别模型替换 MOD 替换了哪些游戏内模型。
- 替换目标识别：第一版覆盖武器、防具、发型、随从武器、随从防具、猎虫、挂件、NPC、投射器和人物语音；同一个 MOD 可能替换多个目标；第一版只做识别和展示。
- 操作预览：启用、禁用、卸载、排序变更、一键还原前展示会影响哪些文件。

MVP 不包含：

- 下载和更新功能。后续如做，只考虑 Nexus Mods，并使用 API 下载和 SSO 登录。
- AI Agent。
- 多个 MHW 游戏路径。
- 模型替换目标选择或改绑（MVP 后由 Slice 14 实现）。
- 自动清理 Acumod 没有记录过的手动安装文件。

MVP 完成标准：

- 用户能设置 MHW 游戏目录并通过校验。
- 用户能导入文件夹 MOD 和 `rar`、`zip`、`7z` 压缩包 MOD。
- 用户能看到 MOD 列表、文件列表、启用状态、冲突状态和模型替换识别结果。
- 用户能启用、禁用、卸载 MOD。
- 用户能通过排序解决文件冲突。
- 用户能一键还原纯净状态。
- 所有删除动作只处理 Acumod 记录过的部署文件。

## 阶段 0：基础链路

目标：确认应用能够运行，前端能调用 Rust。

当前状态：

- 已有 Vue 页面。
- 已有 `get_app_info` Tauri command。
- 已有 Rust DTO 返回。
- 已有 Tauri 2 配置和 npm 构建脚本。

完成标准：

- `npm run build` 能完成前端类型检查和构建。
- `cd src-tauri && cargo check` 能完成 Rust 检查。
- `npm run tauri:dev` 能打开桌面窗口并展示后端返回信息。

## 阶段 1：游戏目录和 MOD 扫描

目标：让用户选择或确认 MHW 游戏目录，并扫描当前游戏目录状态。

已确认规则：

- 支持自动检测 Steam 默认安装路径。
- 自动检测失败后，允许用户手动设置 MHW 游戏目录。
- 游戏目录校验以 `MonsterHunterWorld.exe` 为准。
- 不支持多个游戏路径，首期只管理一个 MHW 安装目录。

建议功能：

- 手动设置 MHW 游戏目录。
- 检测目录是否包含 `MonsterHunterWorld.exe`。
- 识别 `nativePC` 目录。
- 扫描当前游戏目录中已有 MOD 文件。
- 展示扫描结果、未知文件和潜在风险。

## 阶段 2：本地 MOD 导入和复制式启停

目标：实现传统 MOD 管理器的核心能力：导入、启用、禁用、卸载。

已确认规则：

- 本管理器目前只使用复制式部署。
- 安装 MOD：在 Acumod 软件目录保存一份 MOD，不直接写入游戏目录。
- 启用 MOD：把 Acumod 保存的 MOD 文件复制到 MHW 游戏目录。
- 禁用 MOD：删除 MHW 游戏目录下该 MOD 的已部署文件，保留 Acumod 软件目录中的 MOD 副本。
- 卸载 MOD：只删除由 Acumod 安装并记录过的文件；如果该 MOD 仍处于启用状态，需要先清理它部署到游戏目录中的文件。
- 同名文件冲突时，启用前弹出提示。
- 需要独立的冲突解决功能，让用户通过排序决定覆盖优先级。
- 第一版必须支持文件夹导入，以及 `rar`、`zip`、`7z` 压缩包导入。
- 用户可将一个 MOD 文件夹或一个支持的压缩包拖入程序任意位置；释放后必须先显示确认弹窗，用户确认后可正常识别的文件夹直接安装到本地 MOD 库，压缩包复用现有解包导入流程；目录歧义时列出候选内容根并只导入用户选择的一个分支，游戏根目录 fallback 继续要求确认；一次拖入多个项目时拒绝处理并提示用户逐个导入。
- 当前压缩包导入实现使用随 Acumod 打包的 7-Zip 解包组件：先解包到 `AcumodData/mods/staging/imports/`，再复用文件夹导入识别和本地 MOD 库安装逻辑；用户不需要另行安装 7-Zip。
- 压缩包解压目录只作为临时导入空间；成功安装后只长期保留所选分支在本地 MOD 库中的一份副本。进程首次访问 MOD 库或开始下一次压缩包导入时清理遗留暂存。
- 导入前按 MOD 名称进行不区分大小写的重复检查；同名 MOD 已存在时返回已有 MOD 信息并显示“已导入”，不创建新的 MOD 目录。压缩包在解包前执行这项检查。
- 导入识别优先以 `nativePC` 为内容根；如果压缩包或文件夹缺少 `nativePC`，但出现 `weapon`、`wp`、`pl`、`plugins` 等常见 nativePC 内部目录，则自动补成 `nativePC/...` 部署路径；如果用户直接选择这些内部目录本身，也要保留目录名并映射到 `nativePC/<目录名>/...`。
- 如果无法识别 `nativePC` 或常见 nativePC 内部目录，但目录内存在文件，应提示用户确认是否按游戏根目录相对路径导入；确认前不能自动把未知目录当作游戏根目录 MOD。
- 当前启用实现：从 Acumod 本地 MOD 库复制到已配置的 MHW 游戏目录；启用按钮直接执行，Rust 仍生成部署计划并按当前状态覆盖目标文件，不弹出确认。
- 当前禁用实现：只删除该 MOD manifest 中 `deployedFiles` 记录过的游戏目录文件，并保留 Acumod 本地 MOD 库副本。
- 当前卸载实现：先生成卸载预览；如果该 MOD 有已记录部署文件，先清理游戏目录部署副本；随后删除 Acumod 本地 MOD 库中的该 MOD 目录。
- 当前一键还原实现：扫描 Acumod 本地 MOD 库中的 manifest，禁用所有仍启用或仍有部署记录的 MOD，并删除所有记录过的游戏目录部署文件。
- 当前冲突排序实现：扫描所有已安装 MOD 的 `deployRelativePath` 建立 MOD 冲突关系；直接或间接相互冲突的 MOD 归为一组，彼此无关的冲突分开显示。主列表只显示普通序号；用户在独立冲突界面调整整个组的 MOD 优先级，并可按需展开查看该组冲突文件路径。组顺序保存到 `AcumodData/mods/installed/conflict-orders.json`；从上到下为优先级，每个文件由顺序中第一个已启用且实际包含该文件的 MOD 最后覆盖并提供。
- 已安装 MOD 列表可以通过受校验的 Tauri command 在系统资源管理器中打开对应本地库 `content` 文件夹。
- 冲突报告只包含至少两个当前已启用 MOD 之间的实际冲突；尚未启用的 MOD 不进入冲突组，也不在冲突管理界面显示。
- 每次成功启用 MOD 后，将它放到相关冲突组最上方。例如先启用 A、再启用 B，默认顺序显示为 `B -> A`，由 B 覆盖 A；之后用户仍可在冲突管理界面手动调整。
- 如果当前生效 MOD 被禁用或卸载，Acumod 会重新应用它所在冲突组，让顺序中的下一个适用且已启用 MOD 接管；无法安全覆盖时保留警告。

### 狩技 MOD 盒子导入（第一切片）

- 用户输入狩技 MOD 盒子根目录后，Acumod 只读识别 `config.ini` 的 `[582010].gamepath`、`Mods_582010/<模块 ID>/info.xml` 和该模块的 `files/`。
- 列表展示盒子模块名称、模块 ID、盒子记录的启用状态、完整安装文件列表、文件数量和大小。
- Acumod 将盒子记录状态与实际游戏目录状态分开显示：逐文件比对盒子 `files/` 与盒子记录的游戏根目录，结果为文件完全一致、部分文件一致、未检测到部署、文件不一致或无法核验。
- 扫描与核验通过现有后台任务执行，按模块和文件上报进度，不阻塞界面。
- 用户可勾选多个模块导入；导入复用普通文件夹导入规则，使用 `moduleName` 作为名称，继续执行同名去重、模型识别和分类生成。
- 导入后只在 Acumod 本地库保存一份 `files/` 内容，初始状态固定为未启用；不运行盒子、不修改其文件、不复制到游戏目录。
- 第一切片不接管现有部署。后续第二切片才允许在用户确认覆盖顺序、且游戏目录完整符合 Acumod 计算出的最终文件结果时，写入受控的已启用和部署记录。

建议功能：

- 从本地文件夹导入 MOD。
- 从本地压缩包导入 MOD。
- 在真正导入前生成路径预览，展示源文件会被映射到 `nativePC/...` 还是游戏根目录相对路径。
- 展示 MOD 名称、来源、安装状态、启用状态、文件列表。
- 启用 MOD。
- 禁用 MOD。
- 卸载 MOD。
- 记录每个 MOD 启用时实际复制到游戏目录的文件列表。
- 对覆盖操作生成预览和确认；MOD 原始文件由本地 MOD 库保存，不额外备份游戏目录中的被覆盖文件。

## 阶段 3：模型替换 ID 表和目标识别

目标：识别 MHW 模型替换 MOD 实际替换的是哪个游戏装备或模型，并显示具体的游戏内名称。

这是 MHW 传统 MOD 管理器的重要能力，不属于 AI Agent 附属功能。

已确认规则：

- MHW 文件 ID 表由 Acumod 内置维护。
- MHW 已停止更新，因此首期可以先维护一版固定 ID 表。
- 第一版识别范围覆盖武器、防具、发型、随从武器、随从防具、猎虫、挂件、NPC、猎人手臂上的投射器/飞翔爪和人物语音替换。
- 同一个 MOD 可能替换多个模型，需要展示多个识别结果。
- 当前内置索引由 `15.10.00` 数据包、本地中文表和可追溯的 curated 社区映射生成；原始游戏数据不提交，应用使用 `references/mhwi-data/curated/model-index.json`。

核心概念：

- MHW 的模型替换 MOD 通常会通过文件路径和文件 ID 指向某个游戏内模型。
- Acumod 需要维护一份 MHW 文件 ID 表，把底层文件 ID 映射为用户能看懂的游戏内名称。
- 识别结果应展示为“这个 MOD 替换了什么”，而不是只展示一串文件名。

当前实现：

- 生成并内置武器、防具模型索引，扫描 MOD 的目标部署路径。
- 武器按模型资源路径识别武器种类、主模型或附件模型、武器 ID 和共用该模型的游戏名称。
- 防具按 `plXXX_XXXX` 模型 ID 和 `helm/body/arm/wst/leg` 部位标记识别装备部位、ID 和游戏名称。
- 发型按 `pl/hair/hairXXX` 路径识别模型 ID，并映射角色创建界面槽位、DLC/NPC/联动名称；Wiki 未收录的编号仍按路径模式返回 ID。
- 随从武器、随从防具、猎虫、挂件和 NPC 使用本地 `15.10.00` 中文表的模型目录、游戏 ID 和名称。
- 武器、防具、发型、随从装备等只在各自规范资源根目录中识别；`vfx/mod` 等特效附属资源不会映射为游戏装备替换目标，但仍会保留在 MOD 文件列表和部署记录中。
- 同一防具模型只有在头盔、铠甲、护手、腰甲和护腿五个标准部位全部命中时才合并显示为一个“防具套装”；命中一至四个部位时保持逐项显示具体部位。
- 完整套装 DTO 的摘要提取官方套装级名称，例如五条“【冰狼】服装·部位”统一显示为“【冰狼】服装”，不追加“（套装）”，也不再取 `displayNames[0]` 简写成某一部位。
- 投射器/飞翔爪按 `wp/slg/slgNNN_NNNN` 目录识别，同时兼容旧 `slgNNN` 格式。当前索引收录通用、独角仙/燕尾蝶、旅团、盛装、浴场、希里和风火轮等已由原始 MOD 页面核对的资源；其它编号保守显示底层 ID，不按防具同号猜测。普通文件名不参与识别。
- 防具手臂 `arm/mod/*.evam` 使用固定格式保存配套飞翔爪编号。Acumod 只有在同一 MOD 同时包含匹配的 `wp/slg` 模型时，才把 `.evam` 解析结果作为该飞翔爪的“关联防具”展示；只有 `.evam` 而没有实际飞翔爪模型时，不新增任何替换结果。
- 数据层已从 Steam 版 `15.10.00` 原始 chunk 定向提取 462 个有效防具 EVAM，并生成 234 个防具模型的逐性别绑定表；其中 14 条明确没有飞翔爪，5 个模型的男女绑定不同。原始二进制文件不进入仓库，后续防具配套飞翔爪改绑必须使用该表，不再采用 `plNNN -> slgNNN` 同号猜测。
- 人物语音只在 `sound/wwise/Windows` 下精确匹配 `pl_act_vo_f_*_m.nbnk` 或 `pl_act_vo_m_*_m.nbnk`，映射为角色创建界面的男女语音 1 至 20 号。
- 识别结果写入当前 manifest schema 14，并在导入结果和已安装 MOD 列表展示；schema 1 至 12 的旧 manifest 在读取时结合本地库文件路径和 `.evam` 内容重新识别，避免保留早期版本对文件名、`vfx/mod`、防具套装或投射器资源的误判。
- 模型 ID 和装备部位只匹配文件夹名称，文件名不参与模型识别；人物语音因游戏资源格式没有独立 ID 目录，是唯一的精确文件名匹配例外。
- 发型优先显示角色创建界面的数字槽位，再显示经 CAPCOM Steam 页面或本地游戏文本确认的官方简体中文名称；NPC/联动角色英文名不作为游戏 ID 显示。
- 同一个 MOD 可以返回多个 `ModelReplacement`。

人物语音继续作为只读识别类别：Acumod 可以显示男女语音序号，但 Slice 14 和后续传统管理器均不提供语音改绑，也不改写 `.nbnk` 内容。

后续增强：

- 在冲突处理中按“替换同一个游戏模型”提供额外提示。
- Wiki 社区数据与最终发布包的再分发许可确认。

已完成的分类与检索基础：

- 根据文件 ID 表识别结果为新导入 MOD 建立初始分类，例如武器、防具、发型等；用户可继续自由修改多分类。
- 根据模型类型、武器种类、游戏内名称对 MOD 进行筛选和排序。

后续功能：

- 在 MOD 列表中支持按替换目标聚合，例如查看所有替换太刀的 MOD。
- 在冲突排序中优先展示替换同一模型或同一路径的 MOD。

Wiki 与本地 `15.10.00` 数据包中还有可扩展的路径识别类别，均不属于当前 MVP：

- 可继续接入：怪物、脸型、噗吱猪服装、家具、玩家/随从通用附件。
- 特殊装备、物品、装饰品、技能、任务和食堂技能等表主要提供数据 ID，缺少可由普通 MOD 文件路径稳定反推具体对象的映射；在建立文件格式识别前不做路径猜测。
- 数据优先级为本地 `15.10.00` 中文表高于社区 Wiki；Wiki 数据必须记录来源和核验日期，未知项继续保守显示底层 ID。

建议数据：

- 文件 ID。
- 模型类型。
- 子类型，例如武器种类。
- 游戏内名称。
- 原始资源路径或目标部署路径。

## 阶段 4：MVP 单一部署状态、冲突排序和一键还原

目标：更清楚地处理 MOD 之间的文件覆盖关系，并支持恢复纯净状态。

已确认规则：

- 只维护当前这一套启用状态和按冲突组保存的排序；不提供多套配置、状态快照或配置切换。
- 主列表使用普通序号，不提供全局 MOD 优先级。
- 有文件冲突时，用户在独立界面中按相互冲突的 MOD 组分别排序；A/B 与 C/D 这类无关冲突互不影响。
- 支持一键还原到纯净状态。
- 一键还原等于禁用全部已启用 MOD，并删除所有 Acumod 记录过的部署文件。

建议功能：

- 显示 MOD 之间的文件冲突。
- 显示哪些 MOD 互相冲突，以及每组涉及的冲突文件数量，但不在主界面列出具体路径。
- 允许用户调整当前冲突组的整体 MOD 覆盖顺序。
- 调整后为整个冲突组生成应用预览。
- 提供应用计划前的操作预览。
- 提供一键还原纯净状态。

## 阶段 5：下载和更新

目标：帮助用户从外部来源获取 MOD，但不牺牲安全和可控性。

已确认规则：

- MVP 不包含下载和更新功能。
- 后续如实现下载和更新，只支持 Nexus Mods。

## 阶段 6：AI Agent

目标：让用户用自然语言管理 MOD，但所有动作仍通过传统管理器的受控能力执行。

已确认规则：

- MVP 不包含 AI Agent。

建议功能：

- 用户输入：“禁用所有画质类 MOD”。

- 应用展示计划：将启用、禁用或改绑哪些 MOD，为什么，影响哪些文件。

- 执行结果回写给用户。

后续 AI 能力：

- 智能翻译 MOD 名称和说明。

第一阶段 AI 只建议，不直接执行。等传统操作计划、确认和执行记录稳定后，再允许“确认后执行”。

## 已完成：MOD 库表格重构

本切片重构了 MOD 库的信息层级和编辑方式，不改变既有导入、部署或冲突排序语义：

1. 最左列使用一个固定尺寸的启用按钮，同时表示当前状态并提供启停入口；Rust 仍在执行前生成计划，前端只保留必要确认，不展示常驻启停计划或结果。
2. 序号使用独立固定列，按照当前筛选和浏览排序结果显示。
3. 名称和备注首次点击即聚焦并保留原值，使用 `Enter` 或失去焦点提交，`Esc` 取消；名称改回原始导入名称时清除自定义名称。
4. 替换信息只展示两行以内的主要摘要，完整识别结果、资源 ID 和文件信息放入行内展开详情。
5. ID 表识别结果在导入时生成初始分类；分类支持顶级和一层子分类，一个 MOD 可选择多个分类，也可清空或创建全新分类。武器自动归入对应子分类，例如“武器·太刀”。
6. 分类定义对整个 MOD 库生效；用户可重命名或删除任何分类，包括识别生成的初始分类。
7. 操作列只保留打开本地文件夹、展开详情和卸载图标；启停和编辑不在操作列重复出现。

分类修改只更新 MOD 元数据，不能改写 MOD 文件、模型识别结果、启用状态或冲突顺序。具体列宽、状态样式、编辑反馈和分类校验规则见 `docs/ui-design.md`。

### 实现约定

- 全局分类存放于 schema 3 的 `AcumodData/mods/categories.json`，包含稳定分类 ID、名称、可选 `parentId`、创建时间，以及仅供 Rust 迁移和新导入复用的识别来源键；最多只支持一层子分类。
- 每个 MOD 的 schema 14 manifest 保存 `categoryIds[]`。列表 DTO 返回已解析的 `ModCategory[]`，前端按任一分类筛选、搜索和排序。
- 元数据使用字段级 patch：名称、备注和 `categoryIds[]` 可以独立保存。空自定义名称表示回到原始导入名称，空数组表示未分类。
- 新建、重命名、删除分类使用 `list/create/rename/delete_mod_category` Tauri command。删除分类时，Rust 扫描本地 MOD manifest 并清除全部引用；带识别来源的分类还会写入抑制列表，后续导入不会自动重建。
- schema 13 及更早版本首次读取时，把有效 `categoryOverride` 与模型识别得到的分类取并集，写入 schema 14 的 `categoryIds[]`；模型识别版本仍独立维护。
- 前端保存链路为：表格单元格或分类管理对话框 -> `src/api/modLibrary.ts` typed wrapper -> Tauri command -> Rust service -> `manifest.json` 或 `categories.json` -> 刷新 MOD 列表和分类列表。MOD 库拖拽排序单独写入 `AcumodData/mods/mod-library-order.json`，不改写 manifest，也不改变冲突优先级。

## Slice 14：同类型模型替换目标改绑

目标：在不修改本地 MOD 原始副本的前提下，让用户选择新的游戏内替换目标，并让内部校验、启用、冲突检测和禁用恢复使用同一份有效部署计划。

已确认范围：

- 支持武器、防具、随从防具、投射器和发型。
- 武器只能在同一种武器类型内改绑，且主模型/附件模型结构必须兼容。
- 防具按整套模型 ID 改绑，保留 MOD 实际包含的部位和男性/女性资源根。
- 随从防具按同一套 `otNNN` 模型改绑，保留头部/身体部位结构。
- 投射器/飞翔爪只接受合法 `slgNNN` 或 `slgNNN_NNNN` 目标；已知目标显示关联防具名称，未知合法编号允许保守使用底层 ID。
- 发型只允许改绑到玩家发型槽位，不把 NPC 或联动角色专用模型作为可选目标。
- 人物语音只保留识别和展示，不提供改绑入口。

实现约定：

- 只有未启用 MOD 可以修改改绑选择；已启用 MOD 必须先禁用。
- MOD 库的“替换信息”单元格是模型改绑的直接入口；已启用 MOD 仍可进入查看，但选择和保存会锁定并提示先禁用。
- 弹窗单分组只显示一个“替换模型”下拉框，多分组用顶部标签切换；“恢复默认”清除当前改绑，飞翔爪手动编号收进“其他飞翔爪编号”。点击保存后内部调用 `preview_mod_remap` 校验，界面不展示文件数、MRL3 或 EVAM 技术统计。
- 当新旧有效部署路径之间实际移动了防具目录中的 `.epv3` 特效触发文件时，预览必须返回“装备特效需要游戏内确认”的警告；前端复用现有保存确认框展示该提示。恢复默认同样适用，普通防具或飞翔爪改绑不额外提示。
- manifest schema 10 新增 `modelRemaps`，当前 schema 14 继续只保存分组键和目标 ID，不复制或改写本地 MOD 文件。
- Rust 根据原始文件、识别结果和 `modelRemaps` 生成有效部署路径；启用预览、实际复制、冲突检测、冲突顺序应用和禁用后的版本恢复都使用这份计划。
- 路径改绑只替换经过验证的资源目录和文件名 token。`.mrl3` 仅对其中精确命中的贴图资源路径进行长度校验后的改写；飞翔爪改绑只改写已经通过识别关联到该模型的 26 字节 `.evam` 绑定字段；不修改 `.mod3`、`.tex` 或 `.nbnk` 文件内容。
- 防具路径按 `plNNN_NNNN` 的完整模型 ID 重写；位于同一防具目录、且严格符合 `head/body/arm/wst/leg/epv/{f,m}_<部位>NNN.epv3` 的 EPV 文件只重写三位套装号，不把目标变体号写入 EPV 文件名。`vfx`、自定义资源目录和不符合该命名的文件保持原路径。
- 防具改绑时，MOD 自带的 EVAM 优先于原版映射：EVAM 随防具目录移动并保留其中的自定义飞翔爪 ID，已被任意 MOD EVAM 关联的 `slg` 不再参与原版关系推导。
- 防具没有自带 EVAM、但包含源防具原版配套 `slg` 时，Rust 按防具模型和男女查询 `armorSlingerBindings`，自动把该 `slg` 部署到目标防具的原版飞翔爪 ID。目标原版明确无飞翔爪时只警告而不猜测；同一份资源因男女差异需要部署到多个目标，或多份资源会合并到同一目标时阻止保存。
- 独立飞翔爪 MOD 以及用户明确设置的飞翔爪目标继续走手动改绑，显式选择高于防具配套推导。
- 保存前必须展示原目标、新目标、路径变化、MRL3 修正数量和风险提示，由用户再次确认。

## Slice 15：Nexus Mods 下载

目标：先完成传统 UI 中可验证的“选择 Nexus 文件 -> 下载 -> 复用现有导入预览 -> 用户确认安装”闭环，再允许 AI Agent 调用同一入口。

已确认边界：

- 只接受 Monster Hunter: World，固定 Nexus game domain 为 `monsterhunterworld`；不实现通用多游戏下载器。
- 元数据优先使用 Nexus Mods API v3；文件列表和下载链接通过独立适配器兼容当前可用接口，避免把具体 API 版本散落在 command 和 UI 中。
- 开发期可以由开发者手动提供 Personal API key 验证链路；公开版本必须注册 Acumod 应用并使用 Nexus SSO，不能要求普通用户粘贴个人 key。
- Premium 用户可在授权后直接获取下载链接；免费用户必须先访问 Nexus 页面，并由 Acumod 接收网站生成的 NXM 临时 `key` 与 `expires`，不能绕过网页确认。
- API key 只保存在系统凭据存储中，不写入 `config.json`、manifest、日志或前端状态；Vue 只能得到登录状态和用户摘要。
- 下载文件先写入 `AcumodData/mods/staging/downloads/<task_id>/` 的 `.part` 文件，完成后校验大小和 API 提供的哈希，再原子改名；下载完成前不解包、不安装。
- 下载完成后必须调用现有压缩包导入预览。多候选分支、游戏根目录 fallback、同名去重和最终安装确认全部复用已有规则。
- manifest 后续增加可选 `nexusSource`，记录 game domain、mod ID、file ID、版本、原始页面和文件哈希，用于来源展示与更新检查；不保存临时下载链接或凭据。

建议拆为三个可独立验证的子切片：

1. Slice 15A：Nexus 客户端和账号验证。Rust 实现凭据存储、`validate user`、MOD URL 解析、MOD 元数据与文件列表 DTO；UI 只允许查看和选择文件，不下载。
2. Slice 15B：受控下载任务。实现开始、查询进度、失败重试、`.part` 文件、大小/哈希校验和速率限制反馈；Premium 直链与免费用户 NXM 授权统一生成一次性下载计划。下载一旦开始顺序完成，不提供取消。
3. Slice 15C：导入桥接和来源记录。下载完成后进入现有导入预览，用户选择分支并确认安装；成功后写入 `nexusSource`，清理本次下载暂存，并支持按 mod/file/version 检查更新但不自动覆盖。

预计需要新增 Rust 生产依赖：HTTP 流式下载客户端、WebSocket SSO 客户端和系统凭据存储。正式实现前应单独确认依赖选择、许可证、发布体积和 Windows 行为；本次方案阶段不新增依赖。
