# 功能拆分

Acumod 的功能按“先传统管理器，后 AI Agent”的顺序推进。传统管理器必须先具备稳定、安全、可验证的操作能力，AI Agent 后续只调用这些受控能力。

## MVP 范围

MVP 目标：做出一个可真实管理 MHW 本地 MOD 的传统管理器，完成“导入 -> 识别 -> 启用 -> 禁用 -> 卸载 -> 冲突排序 -> 一键还原”的闭环。

MVP 必须包含：

- 游戏目录设置：自动检测 Steam 默认安装路径；检测失败后允许手动设置；以 `MonsterHunterWorld.exe` 校验目录；首期只支持一个 MHW 游戏路径。
- 本地配置和元数据：MVP 先使用 JSON 文件保存配置、MOD 元数据、启用状态、排序和部署记录，后续需要复杂查询时再考虑 SQLite。
- 本地 MOD 库：安装 MOD 时在 Acumod 软件目录保存一份，不直接写入游戏目录。
- 导入方式：第一版必须支持文件夹导入，以及 `rar`、`zip`、`7z` 压缩包导入。
- 复制式部署：启用时从 Acumod MOD 库复制到 MHW 游戏目录；禁用时删除游戏目录中的已部署文件；卸载时只删除 Acumod 记录过的文件。
- 部署记录：记录每个 MOD 启用时实际写入的目标路径，禁用、卸载、一键还原都必须基于记录执行。
- 冲突处理：同名目标文件冲突时先提示；提供独立冲突排序功能，让用户通过排序决定最终覆盖优先级。
- 一键还原：禁用全部已启用 MOD，并删除所有 Acumod 记录过的部署文件。
- MHW 文件 ID 表：内置维护一份 MHW 文件 ID 表，用于识别模型替换 MOD 替换了哪些游戏内模型。
- 模型替换识别：第一版覆盖武器、防具、发型替换；同一个 MOD 可能替换多个模型；第一版只识别出替换的是哪个模型。
- 操作预览：启用、禁用、卸载、排序变更、一键还原前展示会影响哪些文件。

MVP 不包含：

- 下载和更新功能。后续如做，只考虑 Nexus Mods，并使用 API 下载和 SSO 登录。
- AI Agent。
- 多个 MHW 游戏路径。
- 模型替换目标选择或改绑。
- 任何修改模型替换目标的功能，包括通过部署路径、文件名或文件内容进行改绑。
- 自动清理 Acumod 没有记录过的手动安装文件。

MVP 完成标准：

- 用户能设置 MHW 游戏目录并通过校验。
- 用户能导入文件夹 MOD 和 `rar`、`zip`、`7z` 压缩包 MOD。
- 用户能看到 MOD 列表、文件列表、启用状态、冲突状态和模型替换识别结果。
- 用户能启用、禁用、卸载 MOD。
- 用户能通过排序解决文件冲突。
- 用户能一键还原纯净状态。
- 所有删除动作只处理 Acumod 记录过的部署文件。

## 阶段 0：基础链路

目标：确认应用能够运行，前端能调用 Rust。

当前状态：

- 已有 Vue 页面。
- 已有 `get_app_info` Tauri command。
- 已有 Rust DTO 返回。
- 已有 Tauri 2 配置和 npm 构建脚本。

完成标准：

- `npm run build` 能完成前端类型检查和构建。
- `cd src-tauri && cargo check` 能完成 Rust 检查。
- `npm run tauri:dev` 能打开桌面窗口并展示后端返回信息。

## 阶段 1：游戏目录和 MOD 扫描

目标：让用户选择或确认 MHW 游戏目录，并扫描当前游戏目录状态。

已确认规则：

- 支持自动检测 Steam 默认安装路径。
- 自动检测失败后，允许用户手动设置 MHW 游戏目录。
- 游戏目录校验以 `MonsterHunterWorld.exe` 为准。
- 不支持多个游戏路径，首期只管理一个 MHW 安装目录。

建议功能：

- 手动设置 MHW 游戏目录。
- 检测目录是否包含 `MonsterHunterWorld.exe`。
- 识别 `nativePC` 目录。
- 扫描当前游戏目录中已有 MOD 文件。
- 展示扫描结果、未知文件和潜在风险。

## 阶段 2：本地 MOD 导入和复制式启停

目标：实现传统 MOD 管理器的核心能力：导入、启用、禁用、卸载。

已确认规则：

- 本管理器目前只使用复制式部署。
- 安装 MOD：在 Acumod 软件目录保存一份 MOD，不直接写入游戏目录。
- 启用 MOD：把 Acumod 保存的 MOD 文件复制到 MHW 游戏目录。
- 禁用 MOD：删除 MHW 游戏目录下该 MOD 的已部署文件，保留 Acumod 软件目录中的 MOD 副本。
- 卸载 MOD：只删除由 Acumod 安装并记录过的文件；如果该 MOD 仍处于启用状态，需要先清理它部署到游戏目录中的文件。
- 同名文件冲突时，启用前弹出提示。
- 需要独立的冲突解决功能，让用户通过排序决定覆盖优先级。
- 第一版必须支持文件夹导入，以及 `rar`、`zip`、`7z` 压缩包导入。
- 当前压缩包导入实现使用随 Acumod 打包的 7-Zip 解包组件：先解包到 `AcumodData/mods/staging/imports/`，再复用文件夹导入识别和本地 MOD 库安装逻辑；用户不需要另行安装 7-Zip。
- 导入识别优先以 `nativePC` 为内容根；如果压缩包或文件夹缺少 `nativePC`，但出现 `weapon`、`wp`、`pl`、`plugins` 等常见 nativePC 内部目录，则自动补成 `nativePC/...` 部署路径；如果用户直接选择这些内部目录本身，也要保留目录名并映射到 `nativePC/<目录名>/...`。
- 如果无法识别 `nativePC` 或常见 nativePC 内部目录，但目录内存在文件，应提示用户确认是否按游戏根目录相对路径导入；确认前不能自动把未知目录当作游戏根目录 MOD。
- 当前启用实现：从 Acumod 本地 MOD 库复制到已配置的 MHW 游戏目录；启用前生成部署计划，目标文件已存在时要求用户确认。
- 当前禁用实现：只删除该 MOD manifest 中 `deployedFiles` 记录过的游戏目录文件，并保留 Acumod 本地 MOD 库副本。
- 当前卸载实现：先生成卸载预览；如果该 MOD 有已记录部署文件，先清理游戏目录部署副本；随后删除 Acumod 本地 MOD 库中的该 MOD 目录。

建议功能：

- 从本地文件夹导入 MOD。
- 从本地压缩包导入 MOD。
- 在真正导入前生成路径预览，展示源文件会被映射到 `nativePC/...` 还是游戏根目录相对路径。
- 展示 MOD 名称、来源、安装状态、启用状态、文件列表。
- 启用 MOD。
- 禁用 MOD。
- 卸载 MOD。
- 记录每个 MOD 启用时实际复制到游戏目录的文件列表。
- 对覆盖操作生成预览和备份。

## 阶段 3：模型替换 ID 表和目标识别

目标：识别 MHW 模型替换 MOD 实际替换的是哪个游戏装备或模型，并显示具体的游戏内名称。

这是 MHW 传统 MOD 管理器的重要能力，不属于 AI Agent 附属功能。

已确认规则：

- MHW 文件 ID 表由 Acumod 内置维护。
- MHW 已停止更新，因此首期可以先维护一版固定 ID 表。
- 第一版识别范围覆盖武器、防具、发型替换。
- 同一个 MOD 可能替换多个模型，需要展示多个识别结果。

核心概念：

- MHW 的模型替换 MOD 通常会通过文件路径和文件 ID 指向某个游戏内模型。
- Acumod 需要维护一份 MHW 文件 ID 表，把底层文件 ID 映射为用户能看懂的游戏内名称。
- 识别结果应展示为“这个 MOD 替换了什么”，而不是只展示一串文件名。

建议功能：

- 维护 MHW 文件 ID 表。
- 扫描 MOD 文件路径，识别其中的模型替换文件。
- 根据文件 ID 表显示被替换对象的游戏内名称。
- 区分模型类型：武器、防具、发型。
- 对武器类模型进一步区分武器种类，例如太刀、大剑、弓等。
- 在 MOD 详情中展示识别结果。
- 在冲突处理中显示多个 MOD 是否替换了同一个游戏模型。

后续功能：

- 根据文件 ID 表识别结果对 MOD 自动分类，例如武器外观、防具外观、发型替换等。
- 根据模型类型、武器种类、游戏内名称对 MOD 进行筛选和排序。
- 在 MOD 列表中支持按替换目标聚合，例如查看所有替换太刀的 MOD。
- 在冲突排序中优先展示替换同一模型或同一路径的 MOD。

建议数据：

- 文件 ID。
- 模型类型。
- 子类型，例如武器种类。
- 游戏内名称。
- 原始资源路径或目标部署路径。

## 阶段 4：单 Profile、冲突排序和一键还原

目标：更清楚地处理 MOD 之间的文件覆盖关系，并支持恢复纯净状态。

已确认规则：

- 第一版只保留单 Profile，也就是只维护当前这一套启用状态和排序。
- 多 Profile 功能后续可以做，但不进入 MVP。
- 需要支持排序或优先级。
- 有文件冲突时，用户通过排序决定覆盖文件优先级。
- 支持一键还原到纯净状态。
- 一键还原等于禁用全部已启用 MOD，并删除所有 Acumod 记录过的部署文件。

建议功能：

- 显示 MOD 之间的文件冲突。
- 显示每个冲突文件当前由哪个 MOD 最终生效。
- 允许用户调整 MOD 优先级。
- 调整排序后生成重新部署计划。
- 提供应用计划前的操作预览。
- 提供一键还原纯净状态。

## 阶段 5：下载和更新

目标：帮助用户从外部来源获取 MOD，但不牺牲安全和可控性。

已确认规则：

- MVP 不包含下载和更新功能。
- 后续如实现下载和更新，只支持 Nexus Mods。
- 后续 Nexus Mods 下载需要使用 API 下载和 SSO 登录。

## 阶段 6：AI Agent

目标：让用户用自然语言管理 MOD，但所有动作仍通过传统管理器的受控能力执行。

已确认规则：

- MVP 不包含 AI Agent。
- AI Agent 后续接入时，只能调用传统管理器已有的受控能力。

建议功能：

- 用户输入：“禁用所有画质类 MOD”。
- 用户输入：“把这个太刀外观 MOD 改成替换另一把太刀”。
- AI 解析意图并生成操作建议。
- 应用展示计划：将启用、禁用或改绑哪些 MOD，为什么，影响哪些文件。
- 用户确认后执行。
- 执行结果回写给用户。

后续 AI 能力：

- 智能翻译 MOD 名称和说明。
- 翻译时必须使用 MHW 游戏术语表和文件 ID 表辅助理解，避免把武器名、装备名、怪物名、技能名等游戏术语翻译错。
- 翻译结果应保留原文，并在低置信度时提示用户确认。
- 用户可以用自然语言搜索 MOD，例如“我想安装太刀外观 MOD”。
- Agent 可以联网搜索候选 MOD，并给出来源链接，让用户自行下载和导入。
- Agent 后续可以通过 Nexus Mods API 搜索和下载 MOD。
- 通过 Nexus Mods API 安装时，需要用户完成 SSO 登录或授权。
- Agent 下载或安装前必须展示来源、文件名、影响范围和操作计划，并等待用户确认。

第一阶段 AI 只建议，不直接执行。等传统操作计划、确认、回滚机制稳定后，再允许“确认后执行”。

## MVP 推荐任务顺序

1. 检测 MHW 游戏目录。
2. 保存和读取应用配置。
3. 扫描 `nativePC`。
4. 建立 Acumod 软件 MOD 库。
5. 实现本地文件夹导入识别预览。
6. 实现 `rar`、`zip`、`7z` 压缩包导入。
7. 实现启用时复制到游戏目录、禁用时删除部署文件。
8. 实现卸载和备份。
9. 建立 MOD 元数据模型。
10. 引入 MHW 文件 ID 表。
11. 实现模型替换目标识别。
12. 实现冲突排序。
13. 实现一键还原纯净状态。

## MVP 后续任务

1. 实现多 Profile。
2. 基于文件 ID 表结果实现 MOD 分类、筛选和排序。
3. 实现同类型模型替换目标选择或改绑。
4. 接入 Nexus Mods 下载和更新。
5. 接入 AI Agent。
6. 接入 MHW 术语感知的 MOD 名称和说明翻译。
